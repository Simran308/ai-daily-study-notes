## Part 1: Older cards (weeks one and two)

### Card 1: Tokens and cost
**How are thinking (reasoning) tokens billed?**

<details><summary>Answer</summary>

They are billed as output tokens, once, when they are generated. They are part of `max_tokens` and count toward rate limits.

*Why it comes back later:* it explains why higher reasoning effort costs more, and why a low output cap can truncate a reasoning model's reply.
</details>

### Card 2: Prompting
**Why wrap parts of a prompt in XML-style tags like `<document>` and `<example>`?**

<details><summary>Answer</summary>

It removes ambiguity about where instructions, examples and data begin and end. It also lets you ask for output in tags you can parse.

It reduces confusion between data and instructions. It is **not** a security boundary against prompt injection.
</details>

### Card 3: Reasoning models
**Why is reasoning effort a cost dial on GPT-6.1 Sol, and what does a `configuration_update` input item do?**

<details><summary>Answer</summary>

Reasoning tokens are billed as output tokens (5x the input rate here), so higher effort costs more and takes longer.

A `configuration_update` input item changes effort mid-conversation without rewriting the prompt prefix, which keeps the cache valid.
</details>

### Card 4: Agents in production
**Why prefetch context with deterministic code instead of letting the agent look things up itself? (Stripe's Minions)**

<details><summary>Answer</summary>

It is cheaper and more predictable, and the model can't skip a step. Ordinary code gathers the ticket, thread and docs before the model runs.
</details>

### Card 5: Structured outputs
**What are the three levels of getting JSON out of an LLM, from weakest to strongest?**

<details><summary>Answer</summary>

1. Ask in the prompt and parse, with no guarantee.
2. JSON mode, which guarantees valid JSON in any shape.
3. Schema-enforced structured output, which guarantees valid JSON that matches your schema.

Remember that even level 3 does not guarantee the *values* are right.
</details>

### Card 6: Gateways
**Why put a rule like "refunds over $100 need a human" in the gateway code and not only in the system prompt?**

<details><summary>Answer</summary>

A prompt rule is a request the model can ignore, misread, or be tricked out of. A code rule is enforced every time, whatever the model says.
</details>

## Part 2: Cards from the past week

### Card 7: Tool use
**Who actually executes a function the model "calls", and what does the model produce?**

<details><summary>Answer</summary>

Your code does (for client tools). The model only emits a structured request: the tool name plus a JSON object of arguments. You run it and send the result back.
</details>

### Card 8: Caching
**How do you structure a prompt to get cheap cache hits?**

<details><summary>Answer</summary>

Put the stable part first (system prompt, tool definitions, reference documents) and the changing part last, so the repeated prefix can be reused. On DeepSeek a hit costs about 1/50 of a miss.
</details>

## Connect the dots (optional, 3 minutes)

Pick one and answer in two or three sentences.

1. Cards 1 and 3 are two views of the same fact. What is it, and how would it change the way you set `max_tokens` for a reasoning model?
2. Cards 4 and 6 both move a decision out of the model and into ordinary code. What does each one gain by doing that?
3. Cards 7 and 8 together: in a long tool-calling loop, which part of the prompt should stay stable, and why does that matter for cost?

<details><summary>Suggested answers</summary>

1. Reasoning tokens are billed and counted as output. So `max_tokens` must leave room for the thinking plus the visible answer, or the reply can be cut off and a correct model looks wrong. Higher effort also raises the bill.
2. Prefetching gains predictability and lower cost, because the model can't skip a step. The gateway rule gains enforcement, because a code check runs every time regardless of what the model says.
3. The system prompt, tool definitions and reference documents should stay at the front, unchanged. A tool loop resends a growing prefix on every turn, so a stable prefix means most input tokens can be cache hits at a fraction of the normal price.
</details>
